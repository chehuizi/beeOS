## 0. 商业定位

**beeOS 不卖 AI，不卖 Workflow。beeOS 交付成熟的履约盒子。**

> 一个履约盒子，承接一项明确的业务责任，并以可验证的业务结果完成履约。

**核心定位**：
- beeOS = 平台（基础设施 + 履约盒子市场）
- beeBox = 产品（履约盒子 = 客户真正购买的东西）
- 履约结果 = 价值（可验证的业务结果，不是 AI 能力）

---

## 1. 三层产品层次

| 层 | 内容 | 谁买 / 谁用 | 实现位置 |
|---|---|---|---|
| **履约盒子**（beeBox）| 客户真正购买的东西——"帮我完成 X" | 企业客户（业务负责人）| 产品层 |
| **履约盒子市场**（Catalog）| 成熟盒子的集合，按行业 / 业务价值流分类 | 企业客户挑选 + 安装 + 配置 | 产品层 |
| **beeOS 基础设施**（platform）| Contract / Policy / Queen / BeeLine / Runtime / Release / Instance / Evidence / Metrics | beeOS 团队 | 平台层 |

**关系图**：

```
                    beeOS
                      │
              Fulfillment Platform
                      │
              ┌───────┴───────┐
              ▼               ▼
         Box Runtime       Box Factory
              │               │
              ▼               ▼
        成熟履约盒子       新履约盒子
              │
              ▼
          企业客户
```

**关键点**：
- 客户甚至可以不知道 beeOS 内部细节——只用履约盒子
- 平台层（beeOS）演进不影响客户对盒子（beeBox）的使用
- 盒子可以跨行业 / 跨业务复用——但**不是 marketplace 模式**（详见 §6 单行业起步）

## 2. 履约盒子 Catalog

### 2.1 盒子是什么

履约盒子 = beeBox（设计稿第一性定义）= 1 个 bounded Business Fulfillment Unit。每个盒子都有：

| 属性 | 含义 |
|---|---|
| **输入** | 接收什么（业务数据 / 触发事件）|
| **输出** | 交付什么（业务结果）|
| **业务责任** | 负责什么业务 |
| **验收标准**（Acceptance）| 怎么算"做对了"（度量 + 阈值）|
| **例外条款**（Exceptions）| 出异常怎么办（自动处理 / 升级人工 / 退单）|
| **SLA** | 时效 / 可用性 / 容量承诺 |
| **成本** | 单次履约资源消耗 |
| **证据**（Evidence）| 怎么证明做对了（操作日志 + 验收记录）|
| **版本** | 履约盒子版本（升级 = 新版本盒子）|

### 2.2 Catalog 示例（5 类高频业务盒子）

| 履约盒子 | 输入 | 输出 | 核心指标 | SLA |
|---|---|---|---|---|
| **订单异常履约盒** | 异常订单 + 上下文 | 已解决订单 | 解决率 / 时效 / 成本 | < 30 min |
| **发票核验履约盒** | 发票 + 订单 + 合同 | 已核验发票 | 准确率 / 时效 / 误核率 | < 5 min |
| **客户开户履约盒** | 客户资料 + 资质材料 | 已开户客户 | 通过率 / TAT / 完整率 | < 1 hour |
| **退款履约盒** | 退款申请 + 订单 + 支付信息 | 已完成退款（已批准 / 已拒绝 / 已退款）| 正确率 / 时效 / 误退率 | < 2 hour |
| **应收账款履约盒** | 应收记录 + 客户对账 | 已核销账款 | 核销率 / 人工率 / 准确率 | < 24 hour |

> **关键点**：每个盒子都必须明确回答 6 个问题——它**负责什么**、**不负责什么**、**输入是什么**、**输出是什么**、**验收标准是什么**、**出异常怎么办**。模糊的"AI 履约盒 / 智能自动化盒"是 product-speak，不是 Catalog 设计。

### 2.3 盒子的"不负责"清单

每个盒子必须有显式的"不负责"边界——避免变成万能解决方案：

| 履约盒子 | 不负责什么 |
|---|---|
| **订单异常履约盒** | 不负责财务最终记账（应收应付独立）|
| **发票核验履约盒** | 不负责合同审批流（独立成盒）|
| **客户开户履约盒** | 不负责客户风险评估（KYC 独立）|
| **退款履约盒** | 不负责财务最终记账 |
| **应收账款履约盒** | 不负责客户对账发起（对账发起独立）|

> **关键区分**：业务责任是"盒子"的本质，模糊边界会让盒子变成不可控的黑盒。

## 3. 成熟度 Certification（Fulfillment Box Certification）

既然对外承诺"成熟的履约盒子"，"成熟"必须**可验证**——不是 marketing slogan，是产品状态。

### 3.1 每个盒子发布时的 Certification 9 项

| 验证项 | 含义 |
|---|---|
| **Business Result** | 业务结果定义明确（输出什么）|
| **Acceptance** | 验收标准明确（怎么算做对了）|
| **SLA** | 服务等级明确（时效 / 可用性）|
| **Quality** | 质量指标明确（一次做对率）|
| **Exception Coverage** | 例外场景覆盖率（自动处理多少 / 升级人工多少）|
| **Human Escalation** | 人工升级路径（什么时候升级 + 谁接管）|
| **Evidence** | 证据完整（每次履约都有可审计的证据链）|
| **Rollback** | 升级 / 回滚机制（出错能快速恢复）|
| **Observability** | 监控完整（运行时数据可观测）|

### 3.2 Certification 卡片示例

```
订单异常履约盒 v3.2
───────────────
Business Result          ✓ 明确
Acceptance                ✓ 明确（解决率 / 时效 / 异常分类覆盖率）
SLA                       ✓ 99.5%（30 min 内闭环）
Quality                   ✓ 98.7%（一次解决率）
Exception Coverage        ✓ 94%（6% 升级人工）
Human Escalation          ✓ 支持（按异常类型路由到对应队列）
Evidence                  ✓ 完整（每次履约 12 字段记录 + step log）
Rollback                  ✓ 支持（30s 内回滚到老版本）
Observability             ✓ 完整（kanban 看板实时）
Production Runs           ✓ 1,200,000
```

**关键点**：
- "成熟履约盒子"不是 marketing slogan——是**可以被证明的产品状态**
- Certification 可以成为品牌资产：**Certified Fulfillment Box**
- 创业早期盒子少，每个盒子 Certification 做得扎实，比"1000 个盒子"更值钱

## 4. 商业飞轮

```
             beeOS
               │
        ┌──────┴──────┐
        ▼             ▼
   履约盒子 A      履约盒子 B
        │             │
        ▼             ▼
      客户 1         客户 2
        │             │
        └──────┬──────┘
               ▼
        履约数据 / 规则
               ↓
          更成熟的盒子
               ↓
        更高自动化率
               ↓
          更多客户
               ↓
          更多盒子
```

**飞轮解释**：
1. **更多客户** → 跑出更多履约数据 + 真实规则
2. **更多数据** → 改进盒子（提高准确率 + 扩大覆盖）
3. **更成熟的盒子** → 更高自动化率（人工率下降）
4. **更高自动化** → 更低单价 + 更好 ROI → 吸引更多客户
5. 循环

**关键点**：
- 不是"给每个客户重新做 AI 项目"
- 而是"持续把一个个业务履约场景产品化成标准履约盒子"
- 每个客户都在为飞轮贡献数据 + 规则 + 场景

## 5. 单行业起步策略

**不要一开始做"盒子商店"**——创业早期：

```
一个行业
   ↓
一个核心价值流
   ↓
3~5 个高价值履约盒子
   ↓
做深（Certification 9 项全过）
   ↓
证明 ROI（每个客户具体业务结果）
   ↓
标准化
   ↓
复制到第二个客户
```

### 5.1 起步示例：电商订单价值流

**核心价值流**：

```
Order
 ↓
[订单接收盒]
 ↓
[支付异常盒]
 ↓
[库存异常盒]
 ↓
[发货履约盒]
 ↓
[售后处理盒]
```

**5 个盒子的协同**：
- 订单接收盒 → 触发支付异常盒 / 库存异常盒（按需）
- 发货履约盒 → 触发售后处理盒（按需）
- 5 个盒子组合起来 → 整个订单价值流被 beeOS 管理

**为什么这样起步**：
- 电商订单价值流 = 高频 + 高价值 + 业务结果清晰（解决率 / 时效 / 成本可量化）
- 5 个盒子协同形成价值流（不是 5 个独立产品）
- 每个客户都能跑通 ROI（订单履约节省时间 + 降低异常率）

## 6. 避免陷阱

### 6.1 不要让"履约盒子"变成万能解决方案

**坏例子**：
```
❌ AI 履约盒子
❌ 企业自动化履约盒子
❌ 智能业务履约盒子
```
→ **虚**——客户不知道是干嘛的

**好例子**：
```
✓ 订单异常履约盒（负责：订单异常从发现到闭环）
✓ 退款履约盒（负责：退款申请处理到完成）
✓ 发票核验履约盒（负责：发票真实性 + 合规核验）
```
→ **实**——客户清楚"负责什么 / 不负责什么"

### 6.2 不要做"盒子商店"

**坏路线**：
```
"我们有 1000 个履约盒子"
```
→ 变成 marketplace / automation template 故事——失去焦点

**好路线**：
```
1 行业 + 1 价值流 + 3-5 盒
+ 每个盒子的 Certification 9 项全过
+ 复制到第二个客户
+ 然后才是第二个价值流
```
→ **深** > **广**——每个盒子都扎实，每个客户都跑通

### 6.3 不要把 beeOS 当产品卖

**坏路线**：
```
"我们有 beeOS，可以编排 Agent、Workflow、API、Runtime……"
```
→ 客户买的是平台，付钱的是平台使用费——但客户需要的是"帮我完成业务"

**好路线**：
```
"这是订单异常履约盒子。接进去以后，订单异常自动处理到闭环。"
```
→ 客户买的是业务结果，付钱的是履约 ROI

## 7. 跟技术架构的对应

GTM / Catalog / Certification 都跟技术架构一一对应——**业务语言和技术语言是同一对象的不同视角**：

| 产品语言 | 技术语言 | design 章节 |
|---|---|---|
| 履约盒子 | beeBox | §1.1 第一性定义（bounded BFU）|
| "成熟" | Certification 9 项 + 履约事实 12 字段 | §2.4 / §3.4.6 |
| "可验证" | task run 是 durable object | §3.4.1 |
| "业务结果" | Acceptance 阶段 + result 字段 | §3.4.6 |
| "契约" | Contract（result.acceptance + exceptions）| §2.1 / §3.1.2 |
| "自动升级" | queen decision trace + escalate | §3.4.7 |
| "平台能力" | Contract / Queen / BeeLine / Runtime / Release / Instance | §1.4 机制层 |
| "解决方案" | Solution-first / Fulfillment-first | §0 / §1 |

**关键点**：
- GTM 跟技术架构**完全一致**——不是 marketing 包装，是同 1 个对象的两种视角
- 客户看到的是"履约盒子"（业务语言）
- beeOS 团队看到的是"beeBox + Contract + Policy + Procedure + Acceptance"（技术语言）
- 两边都是真的，视角不同

## 8. 创业叙事（一句话）

> **beeOS 是平台，beeBox 是产品，履约结果是价值。**
>
> beeOS 不卖 AI，不卖 Workflow。beeOS 交付成熟的履约盒子。
> 一个履约盒子，承接一项明确的业务责任，并以可验证的业务结果完成履约。

这三个层次分开后：
- 客户清楚买的是什么（履约盒子 = 业务结果）
- beeOS 团队清楚造的是什么（beeBox = 平台单元）
- 投资人清楚值的是什么（每个盒子的 ROI + 飞轮放大）
